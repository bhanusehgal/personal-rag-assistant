**Two important corrections to earlier findings in this session, before any more diagnostics are run:**

1. **The `run_eval.py` / `compare_models.py` scripts must be run with the parent project's venv (`../.venv/Scripts/python.exe`), not the bare `python` on PATH** (which is a plain Python 3.14 install with no `pandas`/project deps). Running with the wrong interpreter fails fast with `ModuleNotFoundError: No module named 'pandas'` — easy to mistake for something else if the log isn't checked immediately.
2. **The "`OLLAMA_CONTEXT_LENGTH` env var doesn't work on this machine" finding from Stage 0 was wrong, or at least incomplete.** Re-tested today: with *all* Ollama processes (including the desktop tray app) fully stopped first (`Get-Process | Where-Object {$_.Name -like '*ollama*'} | Stop-Process -Force`), then starting `ollama serve` with `OLLAMA_CONTEXT_LENGTH=1024` set directly in the shell, the server log confirmed `n_ctx = 1024` — the env var **did** take effect. The original failure was very likely the desktop tray app racing the manually-started server with its own settings-DB-driven instance, not a fundamental env var limitation. `scripts/start_ollama_tuned.bat` now sets `OLLAMA_CONTEXT_LENGTH=1024` directly (see updated comment in that file) — the settings-DB fix (`scripts/fix_ollama_settings_db.py`) is still worth keeping for `OLLAMA_MODELS` and as a fallback, but is no longer the only lever for context length.
3. **New capability**: `eval/run_eval.py` now takes `--golden-path <file>` (defaults to the full `eval/golden_qa.jsonl`) for running a quick subset instead of the full 14-question set — useful for a fast directional check before committing to a full sweep. `eval/golden_qa_probe.jsonl` (first 4 answerable questions) is a ready-made small probe file kept in the repo for this purpose.
4. **Operational gotcha, easy to lose hours to**: `Stop-Process` on `*ollama*` (by name) does **not** kill `llama-server.exe` child processes — a different process name. A zombie `llama-server.exe` from an earlier (misconfigured, `-c 4096`) server survived multiple rounds of "clean" Ollama restarts and silently consumed several GB in the background, causing severe thrashing that looked exactly like the "machine reliability degrades over a long session" pattern documented below. **Always check `Get-CimInstance Win32_Process -Filter "Name='llama-server.exe'"` separately and kill any orphans by PID** before concluding the machine itself is the problem — some, maybe most, of the apparent hardware-reliability degradation blamed on this machine across Stage 0-2 may actually have been orphaned `llama-server.exe` processes accumulating across sessions, not a real RAM ceiling. Worth re-testing machine reliability from a clean process baseline before accepting "this machine is inherently flaky" as a conclusion.

## Stage 2.5 — Hybrid retrieval + retrieval-quality gate (built and verified through the LLM-free stage)

**Why**: Stage 1/2's over-abstention finding held across two model families and a prompt rewrite, ruling out both "the model hallucinates" and "this model specifically is bad at it." That leaves retrieval itself — recall, or how retrieved chunks are *presented* — as the untested variable (hypothesis (c) from Stage 2). Dense-only cosine similarity also gave the pipeline no calibrated confidence signal; every query got 5 scored chunks back with no notion of "good match" vs. "mediocre match." This stage adds a real hybrid retrieval pipeline (dense + lexical, RRF-fused, cross-encoder reranked) and a retrieval-quality gate that can act on an objective score, independent of the LLM's own self-reported `has_sufficient_context`. Full design rationale: `DESIGN.md` section 11.

- [x] New `retrieval/` package: `lexical_index.py` (SQLite FTS5, built from the parent's `metadata.db` read-only), `fusion.py` (Reciprocal Rank Fusion, k=60), `reranker.py` (`cross-encoder/ms-marco-MiniLM-L-6-v2` via `sentence-transformers`), `quality.py` (`RetrievalQualityReport` + `RETRIEVAL_GATE_THRESHOLD`), `hybrid_retriever.py` (`HybridRetriever`, drop-in replacement for `agent.tools.Retriever` at every call site).
